Zero Trust Architecture & Layer 7 DDoS Mitigation

A homelab security project demonstrating outbound-only Cloudflare Tunnel connectivity, Zero Trust access control, WAF rate limiting, and SIEM telemetry verification for a self-hosted Splunk instance.

Project Overview

I built this project to secure a self-hosted Splunk Enterprise instance running on an Ubuntu server without directly exposing the server to the public internet.

Instead of opening inbound ports on the server, I used a Cloudflare Tunnel to create an outbound connection from the origin to Cloudflare. I then added Cloudflare Access to require authentication before users could reach the application and configured WAF rate limiting to control rapid HTTP request bursts.

I then tested the setup by generating a burst of HTTP requests and verifying the resulting traffic in Cloudflare Security Events and Splunk.

Architecture & Tech Stack

Origin: Ubuntu server running Splunk Enterprise
Edge: Cloudflare
Secure Access: Cloudflare Tunnel & Cloudflare Access
Protection: Cloudflare WAF Rate Limiting
SIEM: Splunk Enterprise
Telemetry: /var/log/auth.log and /var/log/cloudflared.log

Implementation Phases

Phase 1: Origin Isolation with Cloudflare Tunnel
I started by connecting the Ubuntu server to Cloudflare using cloudflared. The tunnel creates an outbound connection from the server to Cloudflare instead of requiring an inbound port to be exposed on the origin.

This allowed the Splunk instance to be accessed through a public hostname while keeping the underlying server separated from direct inbound internet traffic.

Phase 2: Zero Trust Access Control
Next, I configured Cloudflare Access to protect the application endpoint. Unauthenticated requests were redirected to an identity challenge before access to the application was granted.

This added an authentication layer at the edge rather than relying solely on the origin server to control access.

Phase 3: Layer 7 Rate Limiting and Attack Simulation
To test the edge security controls, I generated 20 rapid HTTP requests against the public application endpoint.

The initial requests returned HTTP 302 responses, indicating that Cloudflare Access was redirecting unauthenticated traffic to the authentication flow. As the request volume increased, later requests returned HTTP 429 Too Many Requests, showing that the configured rate-limiting rule had triggered.

Phase 4: Edge Security Event Verification
After generating the request burst, I reviewed Cloudflare Security Events to verify how the traffic was handled at the edge.

The dashboard showed blocked requests associated with the configured rate-limiting policy. This provided a second source of evidence that the edge security controls were responding to the test traffic.

Phase 5: Splunk Telemetry Verification
Finally, I verified the activity from the origin side using Splunk. The Ubuntu host was configured to ingest authentication and cloudflared logs, allowing me to compare what was visible at the edge with what reached the server.

I ran a Splunk search for "429" across the ingested host logs. The search returned zero matching events, while Cloudflare Security Events showed the blocked traffic at the edge.

This demonstrated that the tested rate-limited requests were being handled by the Cloudflare security layer without corresponding 429 events appearing in the host-level telemetry.

Security Relevance

This project demonstrates how multiple security controls can work together at different layers of an application environment. Cloudflare Tunnel isolates the origin, Cloudflare Access provides identity-based access control, and WAF rate limiting helps control high-volume HTTP traffic before it reaches the application.

The Splunk integration also provided a way to verify the difference between traffic observed at the edge and telemetry generated by the origin server.
