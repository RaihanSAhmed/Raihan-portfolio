Zero Trust Architecture & Layer 7 DDoS Mitigation for Self-Hosted SIEM

Edge Isolation, WAF Rate Limiting, & Splunk SIEM Telemetry Verification

1. Executive Summary & Technical Impact

This project demonstrates edge isolation, Zero Trust access control, and Layer 7 DDoS mitigation for my homelab Ubuntu-hosted Splunk Enterprise SIEM instance. By leveraging an outbound-only Cloudflare Tunnel (cloudflared), the origin server's public IP address and inbound ports remain completely unexposed to the public internet.

To defend against volumetric and application-layer threats, I used a dual-layer edge defense strategy using a Cloudflare WAF Rate Limiting Policy and Cloudflare Access (Zero Trust OTP). The architecture was tested using a Layer 7 DDoS burst. Splunk host telemetry verified 100% origin server isolation, absorbing all attack traffic at Cloudflare's edge while maintaining real-time host syslog ingestion (/var/log/auth.log and /var/log/cloudflared.log).

I decoupled origin infrastructure from the public internet via outbound-only Cloudflare Tunnels, absorbing 100% of Layer 7 DDoS traffic and enforcing Zero Trust identity challenges at the edge, ensuring zero performance impact or attack log pollution on the self-hosted Splunk SIEM.

Figure 1: Cloudflare Tunnel routing configuration and edge access policies isolating the Ubuntu origin host.

2. Testing & Attack Simulation

I simulated a Layer 7 DDoS burst using a terminal script to fire 20 rapid HTTP requests at the public application endpoint. The initial requests (1 through 11) returned HTTP 302 status codes, confirming that Cloudflare Access intercepted the unauthenticated traffic and redirected it to the Zero Trust OTP login challenge.

As the request volume rapidly increased, requests 12 through 20 breached the threshold and were immediately dropped at the edge with HTTP 429 Too Many Requests status codes. This verified that the rate-limiting policy successfully triggered before the burst could overwhelm the authentication engine or reach the underlying tunnel.

Figure 2: Terminal execution log displaying initial HTTP 302 redirects to Zero Trust OTP followed by HTTP 429 edge blocks.

3. Perimeter WAF Analytics

Inside the Cloudflare Security Events dashboard, real-time analytics confirmed that the edge security layer properly classified and mitigated the attack. The logs record explicit Block actions for incoming traffic, directly attributing the mitigation to the configured rate-limiting rule.

By logging source IP details and enforcing drop actions at Cloudflare's edge, malicious request bursts were fully absorbed before ever entering the cloudflared tunnel, keeping origin network traffic and host completely unaffected.

Figure 3: Cloudflare Security Events analytics showing edge drop actions attributed to WAF rate-limiting rules.

4. Origin Isolation & SIEM Telemetry Verification

To confirm active syslog ingestion on the host, I configured Splunk file monitor inputs targeting /var/log/auth.log for OS authentication events and /var/log/cloudflared.log for tunnel proxy status. Running a structured SPL query verified that host-level telemetry was streaming into Splunk in real time without disruption.

To validate total origin isolation, I executed a targeted SPL query searching for "429" block events across all ingested syslogs. The query returned 0 events, proving that 100% of the DDoS attack traffic was absorbed at Cloudflare’s edge. This confirmed complete origin isolation with no attack noise, bad HTTP traffic, or compute overhead ever reached the underlying Ubuntu server or polluted the SIEM indexes.

Figure 4: Splunk Enterprise SPL search verifying 0 attack log entries reached host syslogs, confirming 100% edge absorption.
